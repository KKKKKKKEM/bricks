## 1. Goal

### 1.1 名称

完成 Bricks Engine 基础设施。

### 1.2 最终目标

完成一个遵循 **less is more、精简内核、插件扩展** 原则的 Python 图状态机 / 数据流 Engine。

Engine 必须能够可靠执行 typed multi-input / multi-output Graph，支持 InputPolicy、渐进式
NodeResult、局部并发、背压、事件观测、持久化恢复，以及取消、超时、重试、幂等等可靠性扩展
边界。最后必须使用 Agent、ETL、Spider 三种不同领域的最小框架或端到端示例验证通用性。

只有达到“可以开始基于 Engine 开发领域型框架”的状态，Goal 才能完成。

### 1.3 完成条件

必须同时满足以下条件：

1. typed multi-port Graph 可以端到端执行。
2. InputPolicy 在运行时真正控制节点触发和输入消费。
3. 不同 Flow 可以使用不同入口、共享部分路线，并返回不同 Endpoint 结果。
4. NodeResult 支持空结果、单个结果、多个结果和渐进式结果。
5. Graph.freeze() 和 Engine 都能在各自层级可靠校验端口类型。
6. 流式输出不会被默认整体缓存；并发和背压具有明确且经过测试的行为。
7. 事件模型足够支持外部日志、metrics 和 tracing 适配器，同时不参与图路由。
8. checkpoint 和恢复具有明确、保守且经过测试的语义。
9. cancellation、timeout、retry、idempotency 具有最小实现或稳定的小型扩展协议。
10. Agent、ETL、Spider 三类验证使用同一套公共 Engine API 并全部通过。
11. 全部自动化检查通过，所有函数和方法具有合格的中文 docstring。
12. 中文文档通俗易懂，与实现和测试一致。
13. 最终质疑审查没有未解决的高严重度问题。
14. 最终审计明确确认可以开始开发领域型框架。

## 3. 不可违反的约束

1. `docs/constitution.md` 是最高设计约束；实现便利与宪法冲突时以宪法为准。
2. 核心只保留无法通过现有原语或插件合理组合得到的机制。
3. Engine 不得感知 Agent、ETL、Spider 等领域概念。
4. 不为假想需求提前抽象；新增核心概念前必须给出至少两个真实领域用例。
5. 公共行为先明确契约，再实现和测试。
6. 所有可执行源码中的函数和方法都必须有中文 docstring，说明用途、参数、返回值、公开异常
   和重要语义约束。
7. 减少重复代码；相同校验和转换必须复用；同类模块保持一致结构。
8. 每个阶段同时交付实现、契约测试、通俗中文文档、可验证示例和能力边界。
9. 语义变化必须同步更新设计文档和宪法，不允许代码与文档分批漂移。
10. 不修改与当前阶段无关的代码，不恢复或覆盖工作区中已有的删除和修改。
11. 未经用户明确要求不得创建 Git commit。

## 4. 主模型职责

主模型是总架构师、规划者、整合者和最终验收者，主要负责：

1. 维护 Goal、阶段计划和本文档中的恢复检查点。
2. 控制核心抽象、公共 API、执行语义和宪法变更。
3. 把边界明确的实现、测试、调查和文档任务交给 sub-agent。
4. 检查每个 sub-agent 的实际 diff、测试证据和语义，不直接接受其口头结论。
5. 组织独立质疑审查，逐项裁决发现的问题。
6. 运行阶段级和项目级验证，并作出“通过 / 不通过”结论。
7. 验收不通过时组织修复并重新验收；通过后自动进入下一阶段。

核心设计决策、宪法解释和最终验收不得直接委托给 sub-agent。

## 5. Sub-agent 协作协议

### 5.1 适合委托的任务

- 仓库调查和影响范围分析；
- 边界明确的局部模块实现；
- 单元测试、契约测试和失败用例补充；
- 中文 docstring 检查；
- 中文使用文档和示例；
- 公共 API 一致性检查；
- 静态检查结果归纳；
- Agent、ETL、Spider 独立验证示例。

### 5.2 委托规则

1. 每项任务必须具体、有限、可独立验收，并写明输入、输出、允许修改的文件和验收标准。
2. 简单且互不冲突的任务应优先并行处理。
3. 不得让多个 agent 同时修改相同文件或同一个公共契约。
4. sub-agent 不得擅自扩大范围、重构无关代码或提交 commit。
5. 主模型必须审查结果；发现不符合宪法或阶段目标时退回修正。
6. 不为了使用 sub-agent 而过度拆分；极小修改由主模型直接完成。

## 6. 强制质疑审查

每个重要阶段至少安排一个独立 Reviewer sub-agent。Reviewer 默认只读，不直接修改代码，并以
“尝试证明本阶段不应通过”为目标，重点检查：

- 是否引入了不必要的抽象或违反 less is more；
- 核心与插件边界是否错误，API 是否绑定特定领域；
- typed port 的静态和运行时检查是否完整；
- 多输入是否可能重复消费、漏消费、错误触发、饥饿或产生不确定顺序；
- 流式输出、并发和背压是否可能死锁、泄漏任务或无限缓存；
- 取消、重试和恢复是否破坏幂等性或重复提交已路由 Output；
- checkpoint 是否可能部分写入或产生状态不一致；
- 错误传播、部分提交和 Run 终止语义是否明确；
- 测试是否只覆盖 happy path；
- 代码、测试、文档和宪法是否存在语义偏差；
- 领域示例是否绕过公共 Engine API。

Reviewer 必须提供具体文件、代码位置、失败场景和验证方法。主模型必须将每项发现标记为：

- `接受`：立即修复并回归测试；
- `拒绝`：记录拒绝理由和证据；
- `延后`：写入 planned 边界、原因和触发重新评估的条件。

存在未解决的高严重度问题时，本阶段不得通过。

## 7. 阶段路线

### 阶段 0：现状审计和执行基线

- 核对工作区、实现、测试、文档和宪法；
- 运行现有检查，记录可靠基线；
- 确认阶段依赖和首个实施切片；
- 不重新设计已有测试支持的稳定抽象。

### 阶段 1：InputBuffer 和 token 消费

- 按 `(run_id, node_id, input_port)` 管理 FIFO token；
- 投递 token，反复调用 InputPolicy，原子消费 InputSelection；
- 防止重复消费，支持节点连续 firing；
- 覆盖 all、any、require、groups 和 on_start。

### 阶段 2：运行时模型

- 实现最小 RunRequest、Run、Task；
- 定义 ID、状态、状态转换和运行级上下文；
- 拒绝非法状态跳转，不引入领域概念。

### 阶段 3：最小单进程 Engine

- 从指定 Flow 和入口启动，调度就绪节点；
- 执行 Node、消费 NodeResult、路由 Output、收集 Endpoint 结果；
- 运行时校验端口值类型；
- 明确未路由 Output、输入不完整、无进展、死锁、成功和失败语义；
- 验证不同入口、共享路线和不同终止节点。

阶段 3 完成后必须进行一次中期架构验收。

### 阶段 4：渐进式输出、局部并发和背压

- 逐项消费 NodeResult.stream，不默认整体缓存；
- 支持有界局部并发和有界队列或等价背压；
- 正确传播生产者异常、取消和下游停止；
- 测试慢消费者、部分提交、异常和取消。

### 阶段 5：事件与可观测性

- 定义最小事件模型和生命周期事件；
- 事件只描述事实，不参与图路由；
- 日志、metrics、tracing 通过小接口适配，不绑定具体产品；
- 验证事件顺序和必要字段。

### 阶段 6：持久化、checkpoint 和恢复

- 提供最小存储协议和内存基准实现；
- 定义 checkpoint 原子边界和恢复行为；
- 避免重复消费已确认 token；
- 对无法安全恢复的流式状态明确拒绝，不伪装支持。

### 阶段 7：可靠性扩展边界

- 明确 cancellation、timeout、retry、idempotency、错误分类和传播；
- 只把不可外置的机制放进核心；
- 提供最小实现或稳定扩展协议及契约测试。

### 阶段 8：领域适用性验证

- Agent：任务生成、工具处理、多输入汇总、流式输出或事件；
- ETL：流式 Extract、Transform、受背压控制的 Load、失败恢复；
- Spider：seed、fetch、parse、item/new-request 分流、并发或去重扩展；
- 三者必须复用同一套 Engine 公共 API，领域逻辑不得进入 Engine。

### 阶段 9：基础设施就绪审计

- 审计公共 API、宪法符合性、中文 docstring 和文档一致性；
- 运行全量检查及三个领域示例；
- 进行最终质疑审查并关闭全部阻断项；
- 给出是否可以开始领域框架开发的明确结论和证据。

阶段可以细分，但不得静默跳过。发现路线需要调整时，先更新本文档并说明原因。

## 8. 每阶段交付与验收门禁

每个阶段必须同时完成：

1. 实现；
2. 单元测试和核心语义的契约测试；
3. 失败、边界、异常和并发场景测试；
4. 通俗中文使用文档；
5. 经验证的最小示例；
6. implemented / planned / unsupported 边界；
7. 必要的设计文档和宪法更新；
8. Ruff、pytest、compileall 和中文 docstring 检查；
9. Reviewer 质疑审查；
10. 主模型复核和最终验收。

阶段报告必须记录：目标、实现、关键文件、公共契约变化、验证结果、质疑发现及裁决、文档更新、
已知限制、验收结论和下一步动作。

验收不通过时立即修复并重新验收；通过后更新本文档并自动进入下一阶段，不等待用户回复。

## 9. 持续执行与停止条件

以下情况不能作为停止理由：完成计划、完成模块、完成阶段、首次测试失败、普通实现问题、文档尚未
完成或 sub-agent 返回不完整结果。此时应继续调查、修复和验证。

只有以下情况可以暂停并询问用户：

1. 需要执行未经授权且难以恢复的破坏性操作；
2. 多个方案会显著改变公共 API 或宪法，且现有原则无法裁决；
3. 缺少外部凭据、服务或数据，且没有本地替代方案；
4. 工作区出现无法解释并与当前任务冲突的外部修改；
5. 同一阻塞条件经过充分调查和多次替代尝试仍无法解决。

因时间、额度或会话中断而退出前，必须先更新“当前进度”“最近一次验证”“未关闭问题”和
“下一步动作”。恢复时从这些字段继续，不能重新从头规划。

## 10. 进度维护规则

本文档是唯一的 Goal 接力状态源。每次更新必须遵守：

1. 阶段开始前，将对应状态改为 `进行中`，填写当前工作和下一步动作。
2. 每个可验收切片完成后，立即更新已完成项、变更文件和验证结果。
3. Reviewer 报告产生后，逐项写入质疑记录和裁决。
4. 阶段通过后，将状态改为 `已通过`，填写通过证据和下一阶段入口。
5. 暂停或会话可能结束前，必须保证“恢复入口”是一条可以立即执行的具体动作。
6. 不记录逐条思考过程；只记录事实、决策、证据、风险和下一动作。
7. 修改公共语义时，同时更新对应设计文档，不能只更新本文档。

## 13. Goal 完成报告

只有第 1.3 节全部满足后，才能把 Goal 标记为完成。最终报告必须包含：

- 核心能力与对应测试证据；
- Agent、ETL、Spider 三个验证结果；
- 最终 Reviewer 报告及全部高严重度问题的处理结果；
- implemented / planned / unsupported 最终清单；
- 全量验证命令和结果；
- “可以开始领域框架开发”或“不可以”的明确判断；
- 如果可以，领域框架只能依赖哪些稳定公共 API。

不得因为里程碑全部标记为已通过就机械完成 Goal；必须再次对照全部完成条件进行最终审计。
